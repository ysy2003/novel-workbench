## 模块与数据

- `app.py`：作品、编辑、记忆、导出与模型记录界面。
- `store.py`：作品、章节、不可覆盖的修订、每章记忆、模型任务、发布记录；SQLite 事务和版本冲突控制。
- `model.py`：读取环境配置、验证目标地址、请求 Chat Completions、解析用量与错误、校验记忆 JSON。
- `writer.py`：以已保存章节和正式记忆组装上下文；生成结果保存为候选或待查看结果。

核心关系：Book → Chapter → Revision；Chapter 关联当前稿与定稿版本；Memory 关联具体定稿版本；Run 记录输入版本、设定版本、提示词版本和候选稿；PublicationRecord 关联被导出或发布的具体版本。

记忆以 `entity / attribute / value` 保存状态变化；按章节顺序覆盖同一对象的同一属性，保留来源。每章摘要保持原文记录，续写加入最近 6 章摘要。未定稿章节不进入正式记忆，前面有未定稿章节时不能续写。前章重定稿且正文或记忆有变化时，后续记忆标为待复核；待复核只作提醒，续写仍参考这些记忆，后续章节可照常定稿和导出，界面显示待复核章节。原样重新确认某章不会连锁标记后续章节，因此可以按任意顺序复核。修改作品设定只递增上下文版本，使基于旧设定的候选稿失效，不把已定稿记忆标为待复核：记忆来自定稿正文，设定变化不改变已经写下的剧情；新设定与前文冲突时，由作者修改并重新定稿相应章节。

第一版任务同步运行，超时上限可配；重启后未完成任务标为已中断，用户可核对用量后重试。没有假设外部请求支持幂等或能无损恢复。当前属于单人本机应用，不作为公开多租户服务部署。

## 分卷大纲与滚动细纲（2026-10-02，用户确认方案）

- 三层：总纲仍是 `books.outline`（全书主线、暗线、伏笔表，每次全文发送）；分卷存 `volumes`（卷号、卷名、章节范围、卷大纲，范围不得重叠）；章节细纲存 `beats`，按章号存，可以先于章节存在。
- 滚动续写：`Store.beat_window` 从已有细纲和已建章节中较大的章号之后开始，一次 1–30 章，不超出所在分卷。`Writer.run_beats` 发送总纲、分卷概览、本卷大纲、本卷已有细纲、最近 6 章摘要，要求 JSON 输出且章号连续覆盖范围，否则标为“结果待修正”。结果只存在调用记录里，`adopt_beats` 采用时只填空位，遇到已有细纲或上下文版本已变时拒绝，不覆盖作者写的细纲。
- 手动编辑：`save_beats` 用表格内容替换某卷范围内的细纲。分卷或细纲的任何修改都递增上下文版本，使之前生成的章节候选稿和细纲候选失效。
- 写章节时：资料附本卷大纲、本章细纲、后续 3 章细纲和分卷概览；规划与初稿指令要求后续细纲只用于铺垫，不提前写。下一章有细纲时，章节工作区提供“按细纲创建”，标题和计划带入细纲。细纲领先已建章节不足 5 章时提示续写。
- 第一版不做：细纲历史版本（AI 原始输出在调用记录中可查）、重新生成已有细纲、自动连写。

## 自动连写（2026-10-02，用户确认方案）

- `novel/autowrite.py`：从已定稿章节之后的下一章开始，按细纲新建章节，依次规划、采用计划、生成初稿、检查、采用初稿、提取记忆、定稿。修订来源标为“自动连写”。
- 前提：已有章节全部定稿；从下一章起有足够的连续细纲；一次 1–10 章。
- 检查：字数在目标的一半到两倍之间；正文不含“作者备注”；每次模型调用状态为“成功”（截断、格式不完整、请求失败都算不通过）；记忆通过校验；计划超过 12000 字等存储校验失败也停下。任一步不通过即停止，已完成章节保留，当前章节停在已完成的步骤，留给作者手动处理。
- 只写新章节，不改已有章节。“自动连写”页列出定稿仍是自动原样的章节；作者修改并重新定稿后移出该列表，后续章节按既有规则标为待复核。
- 同步执行，在页面内逐章显示进度；运行期间断开时已完成章节保留。第一版不做每章自动一致性检查、后台任务。
- 细纲自动续写（2026-10-02，用户确认方案，默认开启）：每写一章前，若从本章起连续细纲不足 4 章（本章 + 写作时参考的后续 3 章），调用 `run_beats` 续写 10 章并用 `adopt_beats` 采用，只填空位、受分卷范围约束。当前章已有细纲时续写失败只记提醒、本次不再重试；当前章没有细纲时续写失败即停止。细纲中间有空洞（后面已有细纲）时不续写，缺细纲的那一章停止并提示补写。结果列出本次续写的范围。

### 分层记忆的具体方向

候选上下文组合：写作偏好 → 精简世界设定与当前卷目标 → 卷摘要 → 最近若干章摘要 → 上一章定稿末尾 → 本章相关人物和地点状态 → 待处理伏笔 → 本章细纲和作者要求。

参考中的“最近 5 章”“末尾 500 字”“提前 10–20 章”是可调起点，不是已经验证的最优参数。当前代码：最近 6 章摘要；事实按本章提及和最近 3 章更新筛选，见 `writer.select_facts`；上一章结尾取定稿版本的末尾 500 字，前半段有换行时从下一段开头截取，见 `writer.tail_text`。规划和初稿指令要求开场承接上一章结尾、不复述。上一章结尾必须取已定稿版本；跨章记忆不能包含未来细纲里尚未发生的事。摘要和事实均保留来源，修订后可识别失效依赖。

选择相关条目时，固定世界规则和必要的主线约束应有独立保留位置，不能只按人物名称命中结果取舍。第一轮已实现：用本章标题、计划、作者要求、正文和近期摘要做对象名称匹配，加上最近 3 章更新；按“被提及优先、较新优先”在字符预算内取舍，省略条数在界面和提示中写明。已知局限：只认完整名称，不识别别名和代称；未被提及的伏笔与世界规则不会单独保留（世界规则应写在设定里，设定全文始终发送）。取得真实长篇错误样本后再判断是否需要别名表或向量检索。每次调用记录所用上下文，方便检查遗漏和误召回。

### 数据模块的候选输入

榜单快照与正文分析分开处理。候选榜单字段：来源 URL、采集时间与时区、平台作品 ID、榜单类型、频道与分类、名次、书名、作者、标签、简介、公开显示的字数与更新时间、公开显示的指标名称和值。页面未提供的字段保持缺失，不能猜测补齐。比较趋势时保持榜单类型、分类与指标口径一致；榜位变化不直接等同于平台阅读人数变化。

拆书分析卡记录：样本来源、涉及章节范围、开篇冲突、人物目标、事件与信息揭露顺序、情绪回报位置、章末悬念，以及观察依据。把跨书结构规律与原书具体人物、事件和措辞区分开，参考模板不应强制所有题材采用同一种“爽点”节奏。

“免费可读”“不保存原文”“只保存分析”不作为已经完成使用范围核验的证据。选取具体来源后再核实允许的访问与使用方式，以及是否允许把材料发送给所选模型服务。

### 保留为待核实的说法

- 各平台是否有公开或授权 API，榜单页面是否可直接请求，正文是否存在字体映射，以及自动操作的适用规则；不能从参考中的一次抓取结果推出长期可用性。
- 当前榜单的分类数量、字段、排名口径与更新机制。
- “某后台信号最准”“便宜模型适合某任务”等判断，需用自己的题材和样章验证。
- 签约数量、收益及其背后的人工投入；不写进本项目的效果指标。

## 下一步候选顺序

1. 接入用户选择的真实模型 API；密钥仅写入本机 `.env`。题材可以在试写前选定。
2. 上一章定稿结尾与相关事实筛选已完成；继续补人物别名和伏笔追踪，使连续创作有可检查的上下文。
3. 增加分卷目标与滚动细纲，再用同一故事进行 10 章试写；若效果可接受再延长到 30–50 章。记录作者改稿时间、可核实矛盾、采纳程度和实际 token 用量，不把工程测试当作写作质量验证。
4. 按真实问题增加文风审校与模型分工；之后再做榜单与拆书输入，帮助选题和结构分析。
5. 确有自动投稿需求时，单独核实番茄当前可用方式与账号流程。
